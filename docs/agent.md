# Agent

The agent is one static binary that runs as root under systemd (`baseline-agent.service`, `Restart=always`). It's built from **collectors**, which read state, and **actions**, which change state. Each collector detects at startup whether it applies to the host, using a binary or socket probe, and reports that as a *capability* in `Hello`. A missing tool means "capability absent", never an error.

## 1. Collectors

| Section | Interval (default) | Source |
|---|---|---|
| `os` | on change / 1h | `/etc/os-release`, `uname`, `/etc/machine-id`, timezone, uptime |
| `hardware` | 24h + on start; on high security hosts 5m, and within seconds of a device or link event | see §1.1 |
| `packages` | 15m (hash-suppressed) | package DBs, see §2 |
| `updates` | 6h, plus after any patch job | repo refresh and comparison, see §2 |
| `containers` | 60s (hash-suppressed) | Docker/Podman Engine API, see §3. Compose stacks travel in this section, derived from container labels. |
| `services` | 5m | systemd |
| `ports` | 5m | `/proc/net/{tcp,tcp6,udp,udp6}`. Socket inode → PID through `/proc/*/fd`. Bind address, port, protocol, process, unit. UDP sockets on ephemeral ports (client sockets) are skipped, except kernel ones such as WireGuard. |
| `certs` | 6h | see §1.3 |
| `reboot` | 15m | see §1.4 |
| `smart` | 30m | `smartctl --scan-open --json` then `smartctl --json -a -n standby -d <type> <dev>` (smartmontools ≥ 7). Covers ATA, NVMe and SCSI. A drive in standby isn't woken; it keeps its last reading. |
| `vms` | 5m | Proxmox / libvirt, see §4. Not sent on hosts with neither. |
| `k8s_node` | 5m | `crictl`, see §3.4. Not sent on hosts that aren't Kubernetes nodes. |
| `k8s` | 5m | Cluster mode only (`--mode=k8s`), see §6 |
| `metrics` | 60s host, 90s containers | see §1.2 |

The server can change intervals through `Config`. "Refresh inventory" on a host page (operator) sends `RequestInventory`.

**Implemented in M1:** `os`, `hardware` and `packages`. The agent runs every collector at connect so `Hello` carries current hashes, sends a section only when its hash changes (or the server asks), and fails a whole section rather than sending a partial one (a partial package list would read as mass removals). `baseline-agent collect [section]` prints what it would send. Sections hold state, not readings, so they don't change on every run: filesystem *usage*, uptime and link state belong to metrics, ZFS dataset sizes are left out (they move with every write), and per-container or per-VM interfaces (`veth*`, `docker*`, `vnet*`...) are skipped. Hardware is stored as one JSON document per host for now; it gets typed tables when a query needs them.

**Implemented in M2:** `updates`, `smart` and host `metrics`, and self-update (§5.2). Collection runs on its own goroutine so a slow repository refresh never holds up heartbeats or metrics; `Hello` carries the hashes of what the agent collected before (none after a restart, so the server asks for everything). The `updates` section is sent after every check, changed or not, so the server knows when it last ran, and it isn't recorded in history: available updates change when a repository publishes, not when the host changes. Metrics are sampled every 60s whether or not the server is reachable and buffered for about 6 hours; the server corrects their timestamps for clock skew using the time each batch was sent.

**Implemented in M3:** `containers` (with Compose stacks), `services`, `ports`, `reboot` and `certs`, and container metrics. History records configuration rather than operations: a container's state, health and restart count, a service's active state and a listener's PID are left out of the comparison (the current state still shows them), images are left out because a container's image ID already says what changed, and Compose files are compared by hash. `reboot` isn't recorded at all: it follows from package changes that are. When an engine can't be read (the Docker daemon is restarting), the section says so and the server keeps that engine's last containers instead of reading the gap as removals. Services and listeners are mapped to their systemd unit through the process's cgroup, on cgroup v2 or v1. `agent.conf` takes `start_podman_socket = true` to start `podman.socket` when it exists but isn't running.

### 1.1 Hardware profile
- **System:** vendor, product, serial, DMI UUID, chassis type, BIOS version and date, baseboard. Read from `/sys/class/dmi/id/*`, falling back to `dmidecode -t 0,1,2,3`.
- **CPU:** model, sockets, cores, threads, flags of interest (virtualization, AES), microcode. Read from `/proc/cpuinfo` and `/sys/devices/system/cpu`.
- **Memory:** total, plus a **DIMM list** with slot, size, type, speed, manufacturer, part and serial from `dmidecode -t 17`. ECC is reported if available.
- **Disks:** model, serial, WWN, capacity, rotational or SSD/NVMe, firmware, transport. From `lsblk -J -b -O`, `/sys/block`, and smartctl identity.
- **Filesystems and mounts:** device, fstype, size, used. From `/proc/self/mountinfo` and `statfs`. ZFS pools come from `zpool list -H -p` and mdraid from `/proc/mdstat`, when present.
- **NICs:** name, MAC, driver, speed, link, IPs. Bond, bridge and VLAN topology. From `/sys/class/net` and `ip -j addr`.
- **PCI devices:** `lspci -mm -nn`, plus GPUs and HBAs called out.
- **High security hosts only** (when the server's `Config` sets `high_security`), so plugging things in doesn't fill an ordinary host's history:
  - **Peripherals:** every USB device plugged into a port, hubs included, from `/sys/bus/usb/devices`: port path (`1-1.2`), vendor and product IDs, manufacturer, product, serial and class. Root hubs (`usb1`) are skipped: they are the controllers, already listed under PCI, and their manufacturer string carries the kernel version. And every display connector (`card0-HDMI-A-1`) from `/sys/class/drm` with its status and the monitor on it, named and serialled from its EDID.
  - **Link state** of physical NICs from `carrier`: up, down (unplugged, or the far end is off) or off (the interface is disabled).
  - **Device events:** the agent listens on netlink for the kernel's uevents (USB devices, disks, PCI devices, NICs and display hotplug) and rtnetlink link changes (loopback and container or VM interfaces aside), and collects hardware once a burst pauses for half a second (at most 3 s after its first event). A USB stick plugged in for a few seconds is seen both coming and going. If the sockets can't be opened, hardware is still polled every 5 minutes.
- **Virtualization:** whether the host is bare metal or a VM, and if a VM, which hypervisor. From `systemd-detect-virt`, falling back to DMI.
- **BMC** (optional): IPMI LAN address and firmware from `ipmitool lan print` / `mc info` when `/dev/ipmi0` exists.

### 1.2 Metrics
Gauges and counters are computed from deltas on the agent and sent as rates.
- **CPU:** user, system, iowait, steal, idle %, load 1/5/15. From `/proc/stat` and `/proc/loadavg`.
- **Memory:** used, available, cached, swap used. From `/proc/meminfo`.
- **Disk I/O per device:** read/write IOPS, read/write bytes/s, utilization %, avg queue. From `/proc/diskstats`.
- **Filesystem:** used and available bytes, used % (as `df` shows it) and inodes used % per mount.
- **Network per interface:** rx/tx bytes/s, packets/s, errors, drops. From `/proc/net/dev`.
- **SMART** (sampled at the SMART interval): temperature, power-on hours, reallocated, pending and uncorrectable sectors, NVMe percentage used and media errors. The section holds the health status and the failure-predicting counters; temperature and power-on hours, which move on their own, are metrics only.
- **Containers (every 90s):** CPU % (100 = one full core, as `docker stats` shows it), memory used (excluding inactive file cache, also as `docker stats` does) and the memory limit per running container. The instance is the container's name, which survives Compose recreating it (prefixed with the engine for Podman), so a service's chart continues across updates. Read **directly from cgroup v2 files** (`cpu.stat`, `memory.current`, `memory.max`) using the container's cgroup path. This is much cheaper than the Engine `stats` endpoint, which we use only as a fallback on cgroup v1.

### 1.3 TLS certificates
- **File scan:** configured globs, defaulting to `/etc/letsencrypt/live/*/fullchain.pem`, `/etc/ssl/certs/*.pem` (excluding the system CA bundle), `/etc/pki/tls/certs/*`, plus extra paths from `Config`. Each file reports subject, SANs, issuer, notBefore/notAfter, serial and fingerprint.
- **Listener probe:** for each TCP port from the `ports` collector bound on a non-loopback or wildcard address, try a TLS handshake against `127.0.0.1:<port>` (or the bound address) with a 2s timeout, at most 64 ports and 8 at a time. Without SNI first, then with each hostname seen in the file scan. Record the leaf cert.
- **Server-side probe:** for agentless endpoints such as a switch, NAS or router UI, configured on a CI (its "TLS endpoint to check" field), the server performs the same handshake itself every 6 hours.
- Self-signed server certificates are kept even when marked CA:TRUE (as `openssl req -x509` does), as long as they name a host and can't sign certificates. A server that refuses a handshake without SNI is still tried with names.

### 1.4 Reboot required
A host is flagged when any of these is true. Each reason is reported.
- `/var/run/reboot-required` exists (Debian/Ubuntu). The packages that caused it are listed from `reboot-required.pkgs`.
- `needs-restarting -r` exits 1 (RHEL family, when available).
- On rpm-ostree hosts, `rpm-ostree status --json` shows a staged deployment that hasn't been booted yet.
- The running kernel (`uname -r`) is older than the newest installed kernel package. This works on every distro.
- Running processes map deleted shared libraries (`/proc/*/maps` with ` (deleted)` on `.so` files). This gives "services need restart" rather than a reboot, and lists the affected units. Only `.service` units count: containers, sessions and `init.scope` are left out.

The kernel check compares kernels of the same flavor only (`-generic` with `-generic`), so an installed `-lowlatency` kernel doesn't look newer than the running one.

### 1.5 systemd services
Parse `systemctl list-units --type=service --all` and `systemctl list-unit-files --type=service`, using JSON output when the installed systemd supports it and plain output otherwise. Report name, load/active/sub state, enabled state and description; units that aren't loaded come from the unit files, template units are skipped and instances inherit their template's enabled state. Main PID and the owning package aren't reported yet. Failed units feed the `failed_units` alert rule. Hosts without systemd as init (containers) report no services.

## 2. Package managers

Every manager implements one interface:

```go
type Manager interface {
    Name() string                                  // "apt", "dnf", ...
    Detect() bool
    Installed(ctx) ([]Package, error)              // name, epoch, version, release, arch, source pkg, repo
    Refresh(ctx) error                             // update metadata (read-only on the system's packages)
    Upgradable(ctx) ([]Update, error)              // name, installed, candidate, repo, security bool, advisory IDs
    Upgrade(ctx, UpgradeSpec, out io.Writer) (UpgradeResult, error) // all | security | listed names; excludes; holds
}
```

| Mgr | Installed | Refresh / upgradable | Security flag | Upgrade |
|---|---|---|---|---|
| apt | `dpkg-query -W -f=...` | `apt-get update`; `apt-get -s -o Debug::NoLocking=1 dist-upgrade` (parse `Inst` lines; a simulation needs no lock); `apt-mark showhold` | candidate origin contains `-security` | `apt-get -y install --only-upgrade <pkgs>` or `dist-upgrade`, with `DEBIAN_FRONTEND=noninteractive`, `--force-confdef --force-confold` |
| dnf/yum | `rpm -qa --queryformat` | `dnf -q makecache`; `dnf -q -C check-update` (exit 100 = updates; dnf4 wraps long names onto their own line); installed versions from `rpm -qa`, newest by rpm's version comparison | `dnf -C updateinfo list --security` (dnf4 and dnf5 layouts) | `dnf -y upgrade [--security] [pkgs]` |
| zypper | `rpm -qa` | `zypper --xmlout refresh`; `--xmlout list-updates` and `list-patches` | patch category = security | `zypper -n update [pkgs]` / `zypper -n patch --category security` |
| apk | `apk info -v` / `apk list -I` | `apk update`; `apk list -u` | (none native; from CVE data) | `apk upgrade [pkgs]` |
| pacman | `pacman -Q` | `checkupdates` (pacman-contrib, uses a temp DB). **Never** `pacman -Sy` on its own. | (from Arch security tracker) | **Full `pacman -Syu` only.** Arch doesn't support partial upgrades, so "selected packages" is disabled for pacman hosts in the UI. |
| rpm-ostree (Bazzite) | `rpm -qa --queryformat` (the booted image's RPM DB is read-only but queryable), plus layered packages from `rpm-ostree status --json` | `rpm-ostree upgrade --check` (exit 77 = none): one update for the whole image, with the new version and digest. Package-level changes (`rpm-ostree db diff`) and hosts with only `bootc` are not covered yet. | — | `rpm-ostree upgrade` (or `bootc upgrade`). The upgrade is **image-wide only**, so "selected" and "security" modes are disabled for these hosts in the UI, and it is staged until reboot. |
| snap | `snap list` (only when `snapd.socket` exists) | `snap refresh --list` | — | `snap refresh [names]` |
| flatpak | `flatpak list --columns=...` | `flatpak remote-ls --updates`; runtimes have no version, so they show commits | — | `flatpak update -y [refs]` |

**Priority** (from the lab's distros: Ubuntu, Rocky Linux, Bazzite): apt, dnf, rpm-ostree, flatpak and snap are built in M1/M2. zypper, apk and pacman are kept in the table for design completeness but deferred to "Later".

Notes:
- **Failures.** A refresh that fails (a repository is down, no network) is a warning in the section and the check goes on from cached metadata; flatpak, snap and rpm-ostree, which only check over the network, warn the same way. A local failure (the package database can't be read) fails the section, and the server keeps the last good copy.
- **Image-based hosts.** When `/run/ostree-booted` exists, the `rpm-ostree` manager is used and `dnf` is never selected, even if the binary is present. For patch-group promotion, the validated unit on these hosts is the **image version/digest**, not package@version. A dependent group deploys exactly that version with `rpm-ostree deploy <version>`.
- Version comparison follows each distro's own algorithm: dpkg, rpm vercmp and apk. They're implemented in Go with test vectors. CVE matching needs the same comparators (`internal/vuln`).
- Held or pinned packages (`apt-mark showhold`, `dnf versionlock`) are reported and never upgraded implicitly.
- Upgrade output streams live to the server as `JobEvent` chunks. The structured result lists each package's before and after version, read back from `Installed()` after the run, so it doesn't depend on parsing tool output.
- Package managers take locks (dpkg lock, rpm DB). The agent runs at most one package job at a time per host and waits up to 10 min for a lock held by something else.

## 3. Containers

### 3.1 Engines
- **Docker:** `/var/run/docker.sock`.
- **Podman:**
  - rootful: `/run/podman/podman.sock`. The agent starts `podman.socket` if the unit exists but isn't active, controlled by a config option.
  - rootless: `/run/user/<uid>/podman/podman.sock` for each logged-in or lingering user.
- Both are reached with one in-house client for the Docker-compatible Engine API (version negotiated through `/version`). Podman-specific data, such as pods, uses the libpod endpoints.
- **Reported per container:** ID, name, image ref, **image ID**, created/started, state, health, restart count and policy, ports, mounts, networks, labels and compose project/service. Environment variables and command lines are never collected: they hold secrets. A container is identified by engine and name, not by its ID, which changes every time Compose recreates it.
- **Reported per image:** ID, tags, **RepoDigests**, size, created. The server joins a container to its image's digests.

### 3.2 Compose stacks
- Stacks are discovered from labels: `com.docker.compose.project`, `.service`, `.project.working_dir` and `.project.config_files`. The agent reads the Compose files (up to 64 KiB each) so the UI can show them, but never edits them. Before a file leaves the host, values of keys that look like secrets (`password`, `secret`, `token`, `api_key`, `private_key`, `credential`, `auth`), literal defaults in `${VAR:-default}` and passwords in URLs are masked; plain `${VAR}` references are kept. It also records which CLI is available: `docker compose`, `podman compose` or `podman-compose`.
- A stack is "defined" when its config files exist and are readable on disk. A stack started from somewhere else is reported as *orphaned* and can't be updated.
- **Stacks that aren't running.** `Config.compose_roots` names the host's Compose roots (set on the server while Compose stack management is on; the agent drops any that fail the root check of §5.3). Each directory directly under a root whose name is a project name and that holds `compose.yaml`, `compose.yml`, `docker-compose.yaml` or `docker-compose.yml` (plus a `compose.override.*` beside it) is a stack. When no stack runs from that directory and none of that name runs on the engine, it is reported with `stopped`, its files read and masked as above and its services taken from the top-level `services:` keys. It goes under the rootless Podman engine of the user who owns the directory, when that user has one that can be read; otherwise under the host's only rootful engine, or Docker when it has both. Agents that do this report `compose-start`.

### 3.3 Image update detection (runs on the server)
The server, not each agent, checks registries (`internal/checks`, every 10 minutes, and within seconds of a host reporting new containers). It dedupes identical image refs across hosts, keeps registry credentials in one place, and caches results for 6h; a failed check is retried after 1h and keeps the last digest it knew. Images built locally or pinned by digest have nothing to compare and aren't checked.
1. **Digest drift (always on).** HEAD `/v2/<repo>/manifests/<tag>`, accepting OCI index, OCI manifest, Docker manifest list and v2. Docker Hub doesn't count HEAD requests against pull limits. Compare `Docker-Content-Digest` with the container's RepoDigest. If they differ, the same tag has a newer image.
2. **Semver tags (opt-in per container or stack service).** Rule: `{track: patch|minor|major, include: regex, exclude: regex}`, set on a container's page; a Compose service's rule is kept on its stack, so it applies to every replica and survives recreation. Lists `/v2/<repo>/tags/list` (following `Link` pagination) for repositories a rule watches, parses semver with `Masterminds/semver`, and reports the newest tag the rule allows. A tag with a suffix (`1.27.3-alpine`) is compared only with tags of the same flavor. Applying it means changing the tag in the Compose file, which Baseline never does on its own. So this produces an *advisory* ("1.5.2 available, you're on 1.4.7") rather than an auto-update.
3. Auth uses the token flow from `WWW-Authenticate: Bearer` (or `Basic`) and credentials configured per registry in **Settings → Registries**, encrypted with `BASELINE_SECRET_KEY`. Anonymous is the default.
4. A stack can be **pinned** (a database, say), which stops update prompts for its containers.

### 3.4 Kubernetes node view
On a Kubernetes node, the `k8s_node` section is what its container runtime runs, read with `crictl`. The agent tries the CRI sockets in order, k3s (`/run/k3s/containerd/containerd.sock`), containerd (`/run/containerd/containerd.sock`), then CRI-O (`/var/run/crio/crio.sock`, `/run/crio/crio.sock`), passing `--runtime-endpoint unix://<socket>`, and uses the first where `crictl version` answers. `crictl` is the one on PATH, else k3s's bundled copy (`k3s crictl`, with `k3s` on PATH or at `/usr/local/bin/k3s` or `/opt/bin/k3s`, for installs that skipped the symlinks) or RKE2's `/var/lib/rancher/rke2/bin/crictl`. A Docker host's containerd has its CRI plugin off, so it doesn't answer, and hosts with no answering socket send no section.

- `crictl version` (text; it has no JSON form) gives the runtime and its version; `crictl pods -o json`, `ps -a -o json` and `images -o json` the pods (namespace, name, ready or not, created), containers (namespace, pod and name from their Kubernetes labels, image, image ID, state, restart count) and images (ID, tags, digests, size). containerd 2 reports a container's image as the pod spec wrote it; older runtimes report an image ID, which is looked up among the images (first tag, else first digest). Only the newest attempt of a container and the newest sandbox of a pod are kept; labels and annotations are dropped.
- A list that fails once the runtime has answered fails the section, and the server keeps its last copy.
- Pods come and go with every rollout and CronJob run, so the section isn't kept in history. Deployments and other workloads come from the cluster agent (§6), and the server links each node to its host by machine-id.

## 4. Hypervisors

The `vms` section holds configuration, plus each guest's run state: usage, uptime, balloon size, runtime tap and vnet names, VNC ports and device aliases are left out, so the section only changes when a guest does. Fields are whitelisted: descriptions and notes, cloud-init passwords, users and SSH keys, extra QEMU `args`, hook scripts, raw `lxc.*` keys, LXC IP settings, storage servers and credentials, graphics passwords and `qemu:commandline` never leave the host. MACs and UUIDs are lowercased and every list is sorted, so the section hashes the same until something changes.

- **Proxmox VE** (detected by `pvesh`), all through `pvesh get … --output-format json`: `/cluster/status` for the local node's name and the cluster's (absent on a standalone node), `/version`, and `/cluster/resources --type vm`, of which **only the local node's guests** are kept: each node reports its own, so a guest that migrates moves with the node running it. Each guest's configuration comes from `/nodes/<node>/qemu/<vmid>/config` or `/lxc/<vmid>/config`, four at a time (every `pvesh` call starts Perl): CPUs (`sockets` × `cores`, or `vcpus`; an LXC container without `cores` gets the resource list's count), memory (also the `current=` form), the SMBIOS UUID from `smbios1`, OS type, machine type, start on boot, tags and HA state; disks (`scsiN`, `sataN`, `ideN`, `virtioN`, `efidisk0`, `tpmstate0`, and an LXC container's `rootfs` and `mpN`; an empty CD drive has no source) with their sizes, and NICs (`netN`) with MAC, bridge, model and VLAN tag. `unusedN` disks and `devN` passthrough are skipped. Storage pools come from `/storage` (name, type, content, shared, path), less those restricted to other nodes; every node of a cluster reports the same shared definitions.
- **libvirt** (detected by `virsh`; the agent runs as root, so `qemu:///system`): `virsh --version`, `virsh list --all --uuid` (and with `--autostart`), then per domain `virsh domstate` and `virsh dumpxml --inactive` (the persistent definition, without runtime details), parsed with `encoding/xml`: domain type, name, UUID (or the `<sysinfo>` SMBIOS UUID when set), memory in any unit, vCPUs (the current count when set), machine type, libosinfo OS ID, disks (file, block device, pool volume as `pool/volume`, or a network disk's name) and NICs (MAC, network or bridge, model, VLAN). Disk sizes aren't read.
- **Failures.** A platform whose listing fails, or one of whose guests can't be read, reports an `error` and none of its guests, so the server keeps its earlier copy instead of seeing guests vanish or half-empty. A missing version only leaves the version empty; a failed `/storage` leaves storage out.
- **Automatic linking:** a guest's DMI product UUID matches the hypervisor's VM UUID, or failing that its NIC MAC matches. When a guest runs its own agent, the server joins the two records with a `runs_on` relationship. Guests without an agent appear as VM CIs with what the hypervisor knows.
- **v1 is read-only.** Start, stop and snapshot actions are roadmap items. A pre-patch snapshot is the most useful one.

### 4.1 Integrations polled for the server

A host on a network the server can't reach can read systems there for it, such as a UniFi console (integrations.md). The agent reports the `unifi` capability, runs each `IntegrationPoll` the server sends on its own goroutine with the shared `internal/unifi` client, bounded by the poll's timeout and at most 5 minutes, and answers with an `IntegrationResult`. The API key arrives with the poll and lives only as long as it; nothing is written to disk or kept in the agent's state. `integrations = off` in `agent.conf` (the value is `on`, the default, or `off`; anything else stops the agent from starting) drops the capability, and the agent refuses any poll that arrives anyway.

## 5. Actions (typed)

Every action has a name, a parameter schema, a capability requirement and a *risk class* that change management uses.

| Action | Params | Notes |
|---|---|---|
| `pkg.refresh` | — | Read-only on the system's packages. Runs automatically on its schedule; "Check now" sends `RequestInventory`, not a job. |
| `pkg.upgrade` | `mode: all\|security\|selected`, `packages[]`, `exclude[]`, `reboot: never\|if_required\|always`, `versions{}` (pins, M5) | Records before and after versions |
| `compose.pull` | `engine`, `project`, `services[]?` | Pulls only. Used to pre-stage images. |
| `compose.update` | `engine`, `project`, `services[]?`, `health_timeout` | See §5.1 |
| `compose.start` | `engine`, `project`, `health_timeout` | For a stack none of whose containers run: `config --quiet`, `up -d`, then the wait of `compose.deploy`. If it doesn't come up, `compose stop` (or `down` when it had no containers) and `rolled_back`. |
| `compose.archive` | `engine`, `project` | `compose down` when it has containers (named volumes and images are kept), then its working directory moved to `.archive/<project>-<UTC yyyymmdd-hhmmss>` beside it. Refused unless the directory is a plain directory holding all of the stack's Compose files, outside the system directories of §5.3. A rootless Podman stack's directory is moved as its user (§5.3), `cp -a` included, so its user must be able to write where it goes. If the move fails, a stack that ran is started again (`rolled_back`). Agents that run it and `compose.move` report `compose-archive`. |
| `compose.move` | `engine`, `project`, `dest`, `health_timeout` | `dest` passes the root check of §5.3. `compose down`, the directory moved to `<dest>/<project>` (a rename, or `cp -a` then removal across file systems), `config --quiet` there, and for a stack that ran `up -d` and the wait of `compose.deploy`. On any failure it is taken down, moved back and started where it was (`rolled_back`). The project name stays, so named volumes stay attached. Same refusals as `compose.archive`. |
| `compose.deploy` | `engine`, `project`, `revision`, `root?`, `compose_sha256`, `env`, `health_timeout` | New stack from a Compose file and .env sent with the job. See §5.3 |
| `compose.edit` | `engine`, `project`, `revision`, `compose_sha256?`, `base_sha256?`, `env`, `health_timeout` | Replaces a stack's Compose file, .env or both. See §5.3 |
| `container.restart` | `engine`, `name` | Through the engine's API socket, so rootless Podman works too |
| `service.restart` / `service.start` / `service.stop` | `unit` | `.service` units only |
| `host.reboot` | `delay_s` | The agent sends a final `JobEvent`, and the job succeeds when the agent reconnects with a new boot ID |
| `agent.update` | `version` | Server-initiated through `UpdateAgent`, not a job (§5.2) |
| `script.run` | `script_id@version`, `args{}`, `timeout` | Body sent with its sha256. The agent verifies the hash, writes it to a tmpfile owned by root, mode 0700, and executes it with the declared interpreter. |
| `inventory.refresh` | `sections[]` | "Refresh inventory" sends `RequestInventory`, not a job |

**Implemented in M4:** `pkg.upgrade`, `service.*`, `container.restart`, `host.reboot` and `script.run` (definitions shared by server and agent in `internal/action`, executed by `internal/agent/runner`). Jobs outlive the connection that delivered them: their events wait in an outbox (output is dropped past 16 MB waiting; results never are) until a stream sends them, output is cut on UTF-8 boundaries a few times a second, numbered so the server drops chunks it already has, and capped at 6 MB per job (the server keeps 5). A journal in `/var/lib/baseline/jobs/` (30 days) makes job IDs idempotency keys across restarts: a job sent again is answered from it; one found "running" by a restarted agent failed with it; one "rebooting" succeeded if the boot ID changed. When a job ends, the agent collects the sections its action can change again and sends them tagged with the job, so the server files the diff under the job's change. Commands run in their own process group with a fixed environment (`PATH`, `HOME=/root`, `LANG=C.UTF-8`), and cancelling or timing out a job stops the whole group. A self-update that arrives while a job runs waits for it.

- **`pkg.upgrade`** reads installed packages, refreshes metadata and lists updates (the `updates` collector), then upgrades with the system manager and with flatpak and snap: `apt-get dist-upgrade` when everything goes, otherwise `apt-get install --only-upgrade <names>` (with `DEBIAN_FRONTEND=noninteractive`, `--force-confdef --force-confold`, a 10-minute dpkg lock wait, and `NEEDRESTART_MODE=l` so services aren't restarted mid-job; the `reboot` section lists them), `dnf -y upgrade [--security] [--exclude=…] [names]`, `rpm-ostree upgrade` (whole image only; security mode skips it), `flatpak update -y --noninteractive [refs]`, `snap refresh [names]`. Held packages and excludes (globs) are left out; packages a request names are `name` (system manager) or `flatpak:`/`snap:` prefixed. Versions are read back from the package databases afterwards, even after a failure, and the result lists what was upgraded, installed and removed; then the reboot policy applies. One package job runs at a time.
- **Local policy.** `agent.conf` takes `allow_scripts = false` (anything but `true`/`yes`/`1` is off) and `allow_actions = patch,container,service,reboot,compose` (or `all`, or `none`); an unknown category stops the agent from starting rather than being ignored. A refused job ends `rejected` with the reason. The policy travels in `Hello`; agents from before M4 send none, and the server sends them no jobs.

**Implemented in M5:** `compose.pull`, `compose.update` and version pins in `pkg.upgrade`. The agent reports the capabilities `pkg-pin` (always) and `compose` (when a Compose CLI is installed for an engine it has); the server sends neither feature to agents without them. A Compose job names a stack by engine and project. The agent reads that stack from the engine at the time: its working directory and files come from the containers' labels and the disk, never from the job. It refuses orphaned stacks, stacks whose files are missing or unreadable, stacks without a working directory or a Compose CLI, and services the stack doesn't have. It runs the stack's own CLI (`docker compose`, `docker-compose`, `podman compose` or `podman-compose`) as `-p <project> -f <file>… [--project-directory <dir>] <command>`, in the working directory with `DOCKER_HOST=unix://<engine socket>`; the Podman CLIs get no `--project-directory` (podman-compose has none) and rely on the working directory. A rootless Podman stack's commands run as its user through `runuser -u <user> --`, with `XDG_RUNTIME_DIR=/run/user/<uid>` and the user's `HOME`. Both actions record each service's image ID and reference, `pull` the selected services and resolve each reference again; `compose.pull` stops there and reports which services would change, and `compose.update` ends "already current" when none would. Otherwise it runs `up -d` (with `--no-deps <services>` when services are named) and waits up to `health_timeout` (checked every 2s) until every container of the services that were running before is running and, if it has a healthcheck, healthy, on two checks in a row without restarting; a container that exits or reports unhealthy fails at once. On failure, including a failed `up`, a cancel or a timeout, it shows `compose logs --tail 50` for the changed services, tags each changed service's old image ID back to its reference through the Engine API (`POST /images/{id}/tag`; references pinned by digest are skipped), runs `up -d --no-deps` for them and checks that they run the old images. The job then ends `rolled_back`, or `failed` with both errors if the rollback didn't work. New images are never pruned. One Compose job runs at a time per host. In `pkg.upgrade`, `versions` pins selected packages: apt installs `name=version` (with `--only-upgrade`), dnf upgrades `name-[epoch:]version-release`, and a pinned image on rpm-ostree hosts runs `rpm-ostree deploy <version>` instead of `rpm-ostree upgrade`. A pinned package is named even when the host's update check found no update for it, or one to another version, so the manager installs exactly that version or fails; held and not-installed pinned packages are skipped with a warning. **Limitations:** apt can't pin a package an upgrade would newly pull in (a new kernel), because it isn't installed yet; `rpm-ostree deploy <version>` assumes the image's remote serves versions, which OCI-based images (`ostree-image-signed:docker://…`) may not; services built locally (`build:`) depend on how the CLI's `pull` treats them.

### 5.1 `compose.update` procedure
1. Record the current **image ID for each service** in the stack.
2. `compose pull` (only the selected services).
3. If no image ID changed, stop with the result "already current".
4. `compose up -d` (only the selected services).
5. Wait up to `health_timeout` (default 120s). Every container must be `running` and, if it has a healthcheck, `healthy`.
6. **On failure, roll back.** `docker tag <old image ID> <ref>` for each changed service, then `compose up -d` again, then report `rolled_back` with logs. Old images are kept until a later, separate prune.

### 5.2 Self-update
The binary lives at `/usr/local/libexec/baseline/baseline-agent`. `/usr/local` is writable on Ubuntu, Rocky and Bazzite (on Bazzite it's backed by `/var/usrlocal`).

1. **Releases.** The release workflow signs the agent binaries while it builds the server image: `baseline-sign` signs each with every key in the `RELEASE_SIGNING_KEY` build secret and writes `baseline-agent-linux-<arch>.sig` (one base64 ed25519 signature per line) next to it. At startup the server copies the binaries and their `.sig` files in its image (`BASELINE_AGENT_DIR`, built with the server's version) to `/data/releases/<version>/` without re-signing, and records them in `agent_release`. It logs a warning for an architecture without a signature that verifies against the keys in `release-keys.pem`, such as a local build. It keeps the 5 newest versions, plus any version a host is still asked to move to.
2. **Desired state.** An admin sets the version hosts should run (Settings → Agents, or a host's overview). The gateway sends `UpdateAgent` (version, arch, sha256, size, the CI signatures, and the server's own signature for older agents) at once to connected agents and on connect to the rest. An agent arriving on its target completes the update; a reported failure clears the target, so a bad release isn't retried on every reconnect.
3. **Install.** The agent downloads the binary with `DownloadRelease` to `baseline-agent.new` **in the same directory**, so the rename stays on one filesystem. It checks the size and sha256, requires one of the CI signatures over `pki.ReleaseStatement` (version, arch and hash, so a signed binary can't pass as another version or platform) to verify against a release key built into the agent, and runs `baseline-agent.new version`. It hard-links the current binary to `baseline-agent.prev`, writes the probation marker `/var/lib/baseline/update-pending.json`, renames the new binary into place, runs `restorecon` when SELinux is enabled (Rocky and Bazzite enforce it), and exits for systemd (`Restart=always`) to start the new one.
4. **Probation and rollback.** The unit runs `ExecStartPre=-…/baseline-agent.prev guard`: the *previous*, known-good binary judges the new one. The new agent must get an answer from the server within 5 minutes; if it doesn't, it exits. Before each start the guard counts starts, and after 3 starts or 5 minutes without the new version connecting it renames `baseline-agent.prev` back and writes `update-failed.json`, which the old agent reports as an `UpdateResult` when it reconnects. A connected new version removes the marker.

Agents installed before M2 can't update themselves (they don't report an architecture); running `install.sh` once more installs the current agent and the guard.

**Turning it off.** `self_update = off` in `agent.conf` makes the agent refuse every `UpdateAgent` (it answers with an `UpdateResult` saying why) and never replace its binary; the host is updated only by running `install.sh` again. The value is `on` (the default) or `off`, and anything else stops the agent from starting, like an unknown `allow_actions` category. Probation and rollback of an update already installed still run. The setting travels in `Hello` with the local policy (`Policy.self_update_off`): the server sets no update target for such a host, drops one set before the owner turned updates off (recording why), and the UI marks the host "self-update off" and hides its update button.

**Release keys.** The trusted public keys are compiled into the agent from `internal/pki/release-keys.pem`, at most two at a time. The server's own release key (`/data/pki/release.key`) is not trusted, and neither is a key the server sends at enrollment, so a server, even with a fresh `/data/pki`, can't produce a binary an agent accepts; only a holder of a CI key can. Since every verified update brings its own key list, the key file in a release decides what the agent trusts next.

- **Rotation.** Add the new public key to `release-keys.pem` and the new private key to the secret next to the old one (two PEM blocks), and release: that release is signed by both and trusts both. Once the fleet runs it, remove the old key from both and release again. An agent that skipped the overlap release still has only the old key, so keep signing with it until no agent is older than the overlap, or move such agents through the overlap release first. If a key leaks, release at once with only the new key in `release-keys.pem` (still signed by the old one, which the fleet trusts), then drop the old key from the secret.
- **Migration from server signing.** Agents older than CI signing check only `UpdateAgent.signature` against the server key they pinned at enrollment (`release.pub`), so the server still signs each release with that key. Updating such an agent to the first CI-signed release is the last update the server key decides: the new binary ignores `release.pub` and that field from then on. An agent that can't take that update can be moved over by running `install.sh` again. A later release can drop the server signature once no agent is older than CI signing.

### 5.3 Stack files: `compose.deploy` and `compose.edit`

These two actions write files, so the files travel with the job rather than in its parameters: `RunJob.stack_files` carries the Compose file and the .env, over the agent's mTLS stream. The parameters only name the revision (`compose_revision` on the server, see change-management.md §5.1), the SHA-256 of the Compose file and whether a .env comes along. The .env is never in the parameters, the journal, the job output or the logs. The agent checks the Compose file against `compose_sha256` and the .env's syntax (`KEY=VALUE` lines, comments and blanks, UTF-8, at most 64 KiB) before it touches the disk. It reports the capability `compose-files` beside `compose`, and both actions fall under the `compose` category of `allow_actions`.

- **Where stacks live.** An admin can give a host Compose roots on its Settings tab, and the deploy picks one (`root` in the job's parameters). Without one, the agent uses its own: `agent.conf` takes `compose_root = /path` (absolute; default `stacks` under the state directory, `/var/lib/baseline/stacks`). The agent checks a root the server sends itself: absolute and clean, not `/`, not under `/etc`, `/usr`, `/boot`, `/proc`, `/sys`, `/dev`, `/run` and the like, and not in its state directory unless it is its own `compose_root`. Agents that take a root report the `compose-roots` capability. A deployed stack gets `<root>/<project>/` (mode 0700) with `compose.yaml` (0644) and `.env` (0600, root-owned; the user's for rootless Podman). The .env is plain on the host: the engine keeps the values in each container's config anyway.
- **`compose.deploy`** refuses when the engine already has a stack with that project name (running or found under a root) or the directory exists. It writes the files, runs `config --quiet`, `pull` and `up -d`, then waits up to `health_timeout` as `compose.update` does, except that a container that exited with status 0 counts as done (one-shot services). On failure it shows `compose logs --tail 50`, runs `down`, removes the directory and ends `rolled_back`.
- **`compose.edit`** works on any stack the engine reports, deployed by Baseline or not, as long as it has exactly one Compose file and the file's SHA-256 still matches `base_sha256` (so an edit never overwrites a change made on the host since it was reviewed). It keeps the old file as `<file>.baseline-prev`, writes the new Compose file and/or `.env` (beside the Compose file, keeping its mode but never wider than 0600), and runs `config --quiet`, restoring the old files at once if that fails. Then `up -d --remove-orphans` and the same wait. On failure it restores the old files (removing a .env that didn't exist before), runs `up -d --remove-orphans` again and ends `rolled_back`. A stack that isn't running (`stopped`) is only written and checked: the edit doesn't start it.
- **Rootless Podman.** A rootless stack (`podman:<user>`) belongs to its user, who also sets the container labels its directory and Compose files come from, so the agent never touches its files as root. It reads and writes them through `baseline-agent stackfile`, its own binary run (through `/proc/self/exe`) as the user with their uid, primary group and supplementary groups, one operation per run: the kernel decides what the job may read or write, and a label pointing at a root-only file fails like it would for the user. Files written that way are the user's. A deploy needs a Compose root the user can write to (e.g. `/home/alice/stacks`, added on the host's Settings tab); otherwise it fails before anything runs, saying so. Compose commands run as the user as they do for `compose.update`. The server offers the rootless engines the latest containers section reports, readable, to agents that report `compose-rootless`. Under a Compose root, a stopped stack whose directory is owned by a user with a readable rootless engine is that engine's stack; any other is the rootful engine's. Inventory reads a rootless stack's Compose files only when the user owns them or anyone may read them, and never blocks on a FIFO.
- Stacks without a Compose CLI are refused. One Compose job runs at a time per host. Removing a stack (`compose.remove`) is not implemented yet.

## 6. Cluster mode

`baseline-agent --mode=k8s` runs inside a Kubernetes cluster as a single-replica Deployment (`deploy/k8s/baseline-agent.yaml`; image from `make image-agent`, the Dockerfile's `agent` stage, which runs as uid 65532 with a read-only root filesystem). It reports the cluster as the `k8s` section every 5 minutes and nothing else: no metrics, no jobs (it sends no local policy), and no self-update (the server never offers one; the image is updated instead).

- **Settings** come from the environment, over `/etc/baseline/agent.conf` if there is one: `BASELINE_SERVER` (the gateway, host:port), `BASELINE_TOKEN` (an enrollment token, used only until the agent has enrolled), `BASELINE_CLUSTER_NAME` (default `kubernetes`), `BASELINE_STATE_DIR` (default `/var/lib/baseline`, a PersistentVolumeClaim, so restarts and rescheduling keep the identity and certificate renewals persist) and `BASELINE_LOG_LEVEL`. Outside a cluster, `BASELINE_K8S_API`, `BASELINE_K8S_CA` and `BASELINE_K8S_TOKEN_FILE` name the API server. `baseline-agent collect --mode=k8s` prints the section.
- **Identity.** On first start the agent enrolls as the cluster: its hostname is the cluster name, its boot ID the constant `k8s-cluster` (so a rescheduled pod replaces the old stream rather than being refused as a clone), machine-id and DMI UUID are empty (inside a pod they'd be the node's), and its one capability is `k8s-cluster`. The server names the host record after the cluster and shows it with only an overview and history.
- **API client.** In-house, read-only, with the pod's service-account token and CA: TLS 1.2 or later, 30 s per request, lists paged 250 at a time (an expired continue token restarts the list once). The token file is re-read after a minute, or at once after a 401, since bound tokens rotate. API errors read like `403 Forbidden: <message>`.
- **What it reads.** The cluster's identity is the kube-system namespace's UID, and its version comes from `/version`; if either can't be read, nothing is sent. Then nodes (roles, ready, cordoned, kubelet, runtime, OS image, kernel, architecture, machine-id, system UUID, internal IPs, CPU and memory capacity, taints), namespaces, Deployments, StatefulSets, DaemonSets, CronJobs and Pods no controller owns (desired and ready replicas, the images of every container and init container, a CronJob's schedule and suspension, a bare pod's node), Services (type, cluster IP, external and load-balancer addresses, ports as `80:30080/TCP→8080`, selector, external name) and Ingresses (class, hosts, TLS, backends as `host/path → service:port`). Environment variables, annotations, ConfigMaps, Secrets and labels other than node roles and service selectors are never read. A list that fails is reported as an error for that resource and the server keeps its earlier copy.
- **RBAC.** The ClusterRole grants `get` and `list` on exactly those resources and `get` on `/version`: no Secrets, ConfigMaps, logs, exec or watch, and nothing that writes.
